# 技术架构与插件化方案（Tauri）

> 更新：2026-10-31  
> 状态：已实施并持续维护；当前版本 v0.1.1  
> 技术栈：Tauri 2 + React 19 + TypeScript + Rust + SQLite

状态所有权与派生规则见 [`状态架构契约`](状态架构契约.md)。

本文定义 Tauri Notes 的最终技术架构。核心目标是在不破坏现有功能语义的前提下，把应用收敛为一个“稳定内核 + 可插拔功能插件”的体系，同时保证桌面平台可移植性和低耦合。

---

## 1. 目标与范围

### 1.1 目标

- 把业务功能从应用外壳中解耦，形成统一的功能插件模型。
- 建立稳定的内核契约，功能插件只依赖契约，不依赖其他插件或内核内部实现。
- 统一命令、事件、端口、面板、菜单、设置、对话框、外观、持久化等横切面。
- 保持 Tauri 桌面应用的单文件可移植安装能力。
- 为 Windows / macOS / Linux 提供一致的平台适配层，隔离平台差异。
- 把主题、皮肤、外观包作为数据插件统一管理。

### 1.2 非目标

- 本期不引入运行时动态加载任意 JS/Rust 代码。
- 本期不重写编辑器、文档、导图的业务逻辑。
- 本期不把移动端作为一等目标，但架构不为移动端制造障碍。
- 本期不开放未经审计的第三方原生插件。

---

## 2. 设计原则

1. **依赖倒置**：所有模块依赖抽象契约，不依赖具体实现。
2. **契约优先**：跨模块通信只能通过命令、事件、端口三类契约。
3. **数据与代码分离**：外观包、模板等可替换内容必须是数据，不是代码。
4. **单一真相**：文档内容以 SQLite 为准，界面只消费解析后的状态。
5. **平台隔离**：平台差异收敛到适配器，内核不含平台分支。
6. **可验证性**：每个插件、迁移、契约都能独立测试。
7. **安全默认**：数据插件禁止执行代码，能力插件必须声明权限。

---

## 3. 现状与差距

当前实现已经具备部分分层基础：

- 前端存在 `domain / application / infrastructure / ui` 分层。
- 存在命令注册表 `ui/commands/registry.ts`。
- 存在跨面板事件总线 `application/panelEvents.ts`。
- 存在端口抽象 `application/ports.ts`。
- 存在统一对话框 `ui/dialog`。
- 存在 Design Token `ui/design-system/tokens`。
- Rust 后端按 `workspace / document_store / map_store / board_store / references / assets / importer` 分模块。

但尚未形成插件体系，主要差距：

- 所有 Rust 命令集中在 `src-tauri/src/lib.rs` 的 `invoke_handler`。
- `App.tsx`、`AppToolbar.tsx`、`DockWorkspace.tsx` 直接组装功能。
- 面板、菜单、快捷键、设置、对话框没有统一贡献点。
- 功能模块之间仍存在直接 import 和隐式依赖。
- 没有插件清单、生命周期、版本、权限、依赖解析。
- 平台差异散落在 `lib.rs`、安装器和 Rust 服务中。
- 外观系统只支持颜色 token，没有皮肤/资源层。

## 4. 目标总体架构

### 4.1 分层图

```text
┌─────────────────────────────────────────────────────┐
│                  Feature Plugins                     │
│  board · reference · import · viewport · help · …   │
└─────────────────────────────────────────────────────┘
                        │ 依赖
                        ▼
┌─────────────────────────────────────────────────────┐
│                     Plugin SDK                       │
│  前端契约 + Rust trait + 生命周期 + 贡献点           │
└─────────────────────────────────────────────────────┘
                        │ 依赖
                        ▼
┌─────────────────────────────────────────────────────┐
│                       Kernel                         │
│  shell · domain · event bus · appearance ·          │
│  document · map · storage · settings · logging       │
└─────────────────────────────────────────────────────┘
```

### 4.2 依赖规则

```text
允许：
  Feature Plugin → Plugin SDK
  Feature Plugin → Kernel Contract
  Capability Plugin → Kernel Contract

禁止：
  Kernel → Feature Plugin
  Feature Plugin → Feature Plugin 内部实现
  任意模块直接 import 其他模块的实现文件
```

插件之间只能通过命令、事件或端口间接协作。

## 5. Tauri 技术定位

Tauri 天然支持两种“插件”概念，必须区分清楚。

### 5.1 原生能力插件 Capability Plugin

对应 Tauri 的 `.plugin(...)`，提供底层系统能力：

```text
dialog
file system
single instance
clipboard
shell
image asset protocol
```

特点：

- 编译期集成；
- Rust 实现；
- 与 WebView 通过命令或事件通信；
- 平台相关能力通过条件编译适配。

### 5.2 应用功能插件 Feature Plugin

对应业务功能：

```text
board
reference
import
viewport
theme
help
search
```

特点：

- 前端 TypeScript 模块 + 后端 Rust 命令模块；
- 编译期打包进应用；
- 通过插件清单声明贡献点；
- 不直接访问内核内部。

### 5.3 数据插件 Data Plugin

对应无代码资源：

```text
.tnlook 外观包
模板
图标集
```

特点：

- 运行时加载；
- 只解析数据；
- 可校验、可回退；
- 不执行任意代码。

## 6. 内核职责

内核只保留不可插拔的基础能力：

```text
Application Shell      窗口、工具栏宿主、状态栏宿主
Panel Runtime          面板注册、布局、恢复
Command Runtime        命令注册、快捷键、执行
Event Bus              强类型事件
Dialog Runtime         统一弹窗
Appearance Engine      token 解析、皮肤资源、背景/装饰层
Document Core          文档解析、保存、索引
Map Core               导图节点、树、位置
Workspace Core         .note 工作区
Storage Core           SQLite 仓储
Settings Runtime       作用域设置
Migration Runtime      迁移执行
Logging / Error        日志与错误码
Plugin Registry        插件注册、激活、停用、依赖
Platform Adapter       平台差异隔离
```

内核不包含任何可插拔的业务功能；workspace、document、map、storage、session、appearance 属于不可移除的核心领域能力，仍保留在内核。

## 7. 插件模型

### 7.1 插件清单

```json
{
  "schema": 1,
  "id": "board",
  "name": "对照板",
  "version": "1.0.0",
  "kind": "feature",
  "provides": ["board"],
  "dependencies": [],
  "capabilities": ["board.read", "board.write"],
  "contributes": {
    "commands": [],
    "panels": [],
    "toolbarItems": [],
    "contextMenuItems": [],
    "settingsSections": [],
    "blockTypes": [],
    "mapNodeTypes": [],
    "appearancePacks": [],
    "migrations": []
  }
}
```

### 7.2 生命周期

```text
register
  → resolve dependencies
  → validate capabilities
  → activate(context)
  → running
  → deactivate(context)
  → unregister
```

激活和停用必须是可重复、可撤销的，资源必须清理。

### 7.3 贡献点

统一贡献点类型：

```text
commands              命令 + 快捷键 + 可用条件
panels                面板 + 标题 + 图标 + 内容
toolbarItems          工具栏菜单与按钮
contextMenuItems      右键菜单
settingsSections      设置区
blockTypes            ProseMirror 节点
mapNodeTypes          导图节点类型
appearancePacks       外观包数据
migrations            数据迁移
storageKeys           插件持久化键
events                发布/订阅主题
```

菜单、面板、设置、快捷键均由贡献点生成，不硬编码。

## 8. 插件 SDK

### 8.1 前端 SDK

```text
registerCommand
registerPanel
registerToolbarItem
registerContextMenu
registerSettingsSection
registerBlockType
registerMapNodeType
registerAppearancePack
emit
subscribe
```

前端插件只 import SDK 和领域类型。

### 8.2 后端 API

```rust
trait AppPlugin {
    fn id(&self) -> &'static str;
    fn register(&self, builder: Builder<...>) -> Builder<...>;
    fn migrate(&self, ctx: &MigrateContext) -> Result<(), PluginError>;
}
```

后端插件通过 trait 注册命令、状态、迁移，不再手工追加到 `invoke_handler`。

## 9. 耦合治理

### 9.1 耦合等级

| 等级 | 形式 | 是否允许 |
| --- | --- | --- |
| 0 | 无耦合 | 允许 |
| 1 | 契约耦合（命令/事件/端口） | 允许 |
| 2 | 服务耦合（依赖领域接口） | 允许 |
| 3 | 直接 import 具体实现 | 禁止 |
| 4 | 直接读写其他模块数据库表 | 禁止 |

### 9.2 端口与适配器

```text
Repository      数据访问
AssetResolver   资源解析
FileSystem      文件操作
Clock           时间
IdGenerator     标识生成
PlatformAdapter 平台差异
```

业务代码依赖端口，基础设施实现端口。

### 9.3 数据所有权

- 内核拥有核心 schema。
- 插件拥有扩展 schema。
- 插件只能通过明确的迁移注册扩展表。
- 插件不能直接读写其他插件的表。

## 10. 通信机制

### 10.1 命令 Command

```text
UI → Kernel → Plugin Service
```

命令是前端触发后端能力的唯一入口。

### 10.2 事件 Event

```text
Plugin A → EventBus → Plugin B
```

强类型主题示例：

```text
document.changed
map.node.created
board.item.pinned
appearance.applied
workspace.opened
```

### 10.3 端口 Port

```text
Kernel Interface → Infrastructure Adapter
```

插件通过端口访问基础设施，不直接调用 Tauri API。

## 13. 平台移植

### 13.1 WebView

| 平台 | WebView |
| --- | --- |
| Windows | WebView2 |
| macOS | WKWebView |
| Linux | WebKitGTK |

内核通过 `WebViewAdapter` 隔离：

```text
窗口创建
数据目录
拖放处理
上下文菜单
剪贴板
```

### 13.2 文件与路径

平台差异必须收敛：

```text
工作区路径
用户目录
临时目录
可执行文件目录
外观/皮肤资源目录
```

内核使用 `PlatformPaths` 接口，不直接拼接平台路径。

### 13.3 文件关联与 Shell

| 平台 | 能力 |
| --- | --- |
| Windows | 注册表 / `reg` |
| macOS | LaunchServices / `open` |
| Linux | xdg / desktop entry |

文件关联作为能力插件，按平台条件编译，内核只接收“打开文件”事件。

### 13.4 原生能力矩阵

| 能力 | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 对话框 | 支持 | 支持 | 支持 |
| 文件系统 | 支持 | 支持 | 支持 |
| 剪贴板 | 支持 | 支持 | 支持 |
| 单实例 | 支持 | 支持 | 支持 |
| 图片协议 | 支持 | 支持 | 支持 |
| 文件关联 | 注册表 | LaunchServices | desktop entry |
| 窗口拖放 | WebView2 | WKWebView | WebKitGTK |

能力插件通过条件编译提供平台实现。

### 13.5 单文件便携性

- 原生能力插件编译进可执行文件；
- 功能插件打包进前端资源；
- 数据插件放在应用数据目录；
- 不依赖外部运行时或注册表残留；
- 卸载后仅保留用户数据。

## 14. 安全与权限

插件必须声明能力：

```text
fs.read.workspace
fs.write.workspace
event.subscribe
command.execute
asset.read
```

原则：

- Rust 原生插件编译期集成，无运行时任意代码；
- 前端功能插件编译期打包；
- 数据插件只解析不执行；
- SVG 必须清洗；
- 资源路径必须校验；
- ZIP 必须有解压限制；
- 未来第三方 JS 插件必须运行在沙箱 Worker。

## 17. 分阶段演进

忽略重构风险的目标顺序：

1. 定义内核边界和插件契约。
2. 抽取 `PlatformAdapter`，收敛平台差异。
3. 建立前端插件 SDK 与后端 `AppPlugin` trait。
4. 统一命令、事件、端口、面板、菜单、设置贡献点。
5. 以 `theme` 为参考实现，完成外观数据插件和设置功能插件。
6. 迁移 `board`、`reference`、`import`、`viewport`、`help`、`search`。
7. 建立迁移注册表和插件状态命名空间。
8. 建立权限与能力声明。
9. 建立外观包导入、校验、预览、导出流水线。
10. 统一构建、测试、视觉回归和安装验证。

## 18. 验收标准

- 新增功能只修改插件目录，不修改内核。
- 所有命令、事件、面板、菜单、设置均由贡献点生成。
- 插件之间无直接 import。
- 平台差异只存在于适配器和能力插件。
- `.tnlook` 可导入、校验、预览、应用、回退。
- 单文件安装不依赖外部运行时。
- 前端、Rust、E2E 测试覆盖插件契约与迁移。
- 每个插件拥有独立版本和迁移记录。

## 19. 术语

| 术语 | 含义 |
| --- | --- |
| Kernel | 不包含业务的内核 |
| Feature Plugin | 业务功能插件 |
| Capability Plugin | 原生能力插件 |
| Data Plugin | 无代码数据插件 |
| Contribution Point | 插件向宿主注册的扩展点 |
| Port | 内核接口与基础设施实现的边界 |
| Adapter | 平台或技术实现 |
| Event Bus | 强类型事件总线 |
| Appearance Pack | `.tnlook` 外观包 |

# 输入与移动端架构审计

> 审计日期：2026-11-01  
> 范围：键盘、命令、快捷键、Intent 总线、桌面 shell、移动 shell、会话恢复  
> 目标：找出输入层与移动端体验的结构性问题，给出不考虑迁移成本的理想架构

## 1. 结论摘要

当前应用已经有命令注册表、shell actions 和一层 `Intent` 总线，但输入处理仍是**桌面键盘优先的旁路实现**，移动端是另一套**直接按钮回调**。两者没有共享同一套语义动作，也没有用户可编辑的 keymap。

最需要优先解决的不是“再加几个快捷键”，而是：

1. **建立平台无关的 Action 层**，所有入口只触发 action；
2. **把键盘/触摸/菜单/手势统一解析成同一种输入请求**；
3. **把 bindings 从 action 实现中分离**，支持平台默认值、用户覆盖和冲突检测；
4. **移动 shell 改为 action + 导航栈 + 持久化状态**，而不是本地 `useState` + 直接调用。

## 1.1 实施状态（2026-11-01）

已落地：

- `src/kernel/action` 提供 Action Registry、Binding、Input Router 和冲突检测；
- 桌面快捷键从命令 metadata 迁移到内置 keymap TOML（`DEFAULT_BINDINGS` 仅作加载前 fallback），由 Router 分发；
- `CommandDefinition` / `CommandContribution` 不再携带 `shortcut`；
- 移动端表面入口（settings/search/help/board/theme）通过 Action surface 触发；
- `mobileShellStore` 持久化移动端 tab、document 和返回栈，切换工作区会重置；
- Rust `load_keymap` / `save_keymap` 读写 `keymap.toml`，`toml_edit` 保留用户注释；
- 前端 `keymapService` 加载 TOML 默认值与用户覆盖，`applyKeymap` 合并；内置默认位于 `resources/keymap/default.toml`；
- 设置 → 快捷键支持查看、录制重设、恢复默认，并通过 `keymapChanged` 事件热更新；
- `useKeymapStore` 统一 keymap 状态，桌面工具栏读取有效绑定生成 shortcut hint；
- 快捷键支持导出到任意 TOML 文件，也支持从 TOML 导入并写入应用配置；
- 移动端文档列表支持长按/右键/左滑动作面板（打开、重命名、移到回收站）；
- 移动端支持横向滑动返回（编辑态限定边缘手势）；
- 旧 Intent 总线已删除，contextmenu 屏蔽保留在 shell；
- 新增 Action/Router/Keymap 单元测试，当前基线 203 / 47 / 37。

待完成（后续增强，不阻塞核心输入重构）：

- 插件贡献 binding 的能力声明与 owner 冲突展示；

## 3. 主要问题

> 以下 IN-* 记录重构前的问题，用于解释目标架构；当前落地状态见 1.1。

### IN-01 两套输入通道并行，Intent 层基本是空壳

`useAppShell` 把 Escape/ContextMenu/Back 解析成 `Intent` 并 `dispatchIntent`，但全项目没有任何 `registerIntentHandler` 调用；与此同时，`useAppCommands` 用另一条 `keydown` 通道执行 Command。

结果是：

- Escape、ContextMenu、Alt+Left 的 Intent 没有消费者；
- 同一个按键可能先被 Intent 处理后又被 Command 处理，顺序取决于两个 effect 的注册顺序；
- 新增输入方式时，必须同时改两套系统。

应保留 **一个** 输入入口：Intent Router（或 Input Router），Command 只是可执行 Action 的一种。

### IN-02 shortcut 是命令上的字符串，没有平台、scope、优先级

`CommandDefinition.shortcut?: string` 把绑定写死在命令定义里：

- `"mod+,"`
- `"Mod+P"`
- `"Mod+Shift+B"`
- `"Mod+Shift+T"`
- `"Mod+Alt+V"`

`matchesShortcut` 只支持 `mod/shift/alt`，用 `ctrlKey || metaKey` 表示 `mod`，并直接比较 `event.key`。

问题：

- Windows/Linux 的 Ctrl 和 macOS 的 Cmd 没有独立语义；
- 无法表达 Ctrl 与 Cmd 不同绑定；
- 没有 `scope`（全局/编辑器/面板/对话框）；
- 没有平台默认值与用户覆盖；
- 没有显示用的按键标签；
- 没有 `when` 条件，只能靠 `enabled(context)` 粗略判断。

### IN-03 全局键盘处理缺少输入法、编辑态和重复键保护

`useAppCommands` 在 `window` 上监听 `keydown`，`matchesShortcut` 没有检查：

- `event.isComposing` / `keyCode === 229`；
- `event.repeat`；
- 当前焦点是否在可编辑区（`isEditableTarget` 只在 Intent adapter 中存在）；
- 修饰键之外的键盘布局差异（`event.code` vs `event.key`）；
- 输入法组合期间是否应该让给 IME。

中文输入法、移动端软键盘和 macOS 的 Option 组合键都可能被误判为快捷键。

### IN-04 命令冲突没有诊断

- `registerCommand` 直接 `Map.set`，同 id 后注册者覆盖前者；
- `findCommandForEvent` 按 Map 插入顺序返回第一个匹配项；
- 两个命令使用相同 shortcut 时没有警告；
- 插件命令只检查“是否与已有核心命令 id 冲突”，不检查 shortcut 冲突；
- 插件命令的 `shortcut` 原样透传（`PluginProvider.tsx:109`），没有命名空间校验。

用户自定义快捷键一旦开放，冲突会从“静默失效”变成可见问题，必须在加载期检测并给出解决 UI。

### IN-05 移动端没有 Action 层，入口直接绑按钮

`MobileShell` 直接在按钮 `onClick` 里调用：

```ts
shellActions.openSettings()
shellActions.openSearch()
shellActions.openHelp()
shellActions.openBoard()
shellActions.openTheme()
```

以及本地的 `switchTab/openDocument/requestSave`。

问题：

- 桌面端走 command id，移动端走函数调用，两边语义没有单一来源；
- 移动端无法复用命令的 enabled、错误处理、日志和权限；
- 同一个 action 在桌面和移动端的可用条件可能不一致；
- 无法在移动端做统一的自定义入口、手势或快捷面板。

### IN-06 移动端状态不持久，也没有导航栈

`MobileShell` 的 `tab`、`documentId`、`editing` 都是本地 `useState`：

- 切到桌面布局再切回移动布局，页面回到默认 map tab；
- 刷新/重启后不会恢复上次移动端页面；
- 没有 back stack，系统返回键/浏览器返回没有语义；
- `documentId` 只存在组件内，无法从通知、深链、最近文档恢复；
- `activePanelId` 只服务桌面 dock，不覆盖移动端的 document/tab 状态。

### IN-07 桌面与移动的操作语义不一致

桌面有：

- Dockview 面板：大纲、导图、控制台、文档库、文档；
- 菜单/工具栏命令；
- 全局快捷键；
- 面板布局保存。

移动有：

- 三个 tab：map/library/document；
- 顶部按钮：设置/搜索/帮助/看板/主题；
- 底部 tabbar：导图/目录/文档/设置；
- 无大纲、控制台、面板布局概念。

部分命令在移动端仍可触发，但 handler 依赖 `dockRef`，而移动 shell 不渲染 DockWorkspace，所以会静默无效。这是典型“同一个 command id，两个 shell 语义不同”的架构债。

### IN-08 插件贡献没有输入契约

插件可以贡献：

- toolbar item；
- command（含 shortcut）；
- panel；
- settings section；
- overlay。

但没有：

- action id 命名空间；
- platform 适用范围；
- scope/priority；
- shortcut 冲突解决；
- 移动端展示类型（菜单项/底部动作/手势）；
- 用户覆盖隔离。

插件在移动端可能注册了桌面快捷键，却没有对应的移动入口。

### IN-09 contextmenu 被全局禁用，Intent 的 contextMenu 没有消费者

`useAppShell` 对所有 `contextmenu` 事件调用 `preventDefault()`；`keyboardIntent` 会生成 `contextMenu` Intent，但没有任何 handler。

结果是：

- 桌面右键菜单被禁用；
- 移动端长按上下文菜单不可用；
- “contextMenu” Intent 是死路径；
- 如果未来要支持触屏长按，需要重新设计，而不是继续全局屏蔽。

### IN-10 缺少快捷键提示、可发现性和无障碍约束

目前：

- 菜单/按钮没有统一的 shortcut hint；
- 没有“快捷键”设置页；
- 没有冲突提示、录制、重置；
- 没有为触控目标、safe-area、软键盘 insets 建立规则；
- 移动端 tabbar 与顶部按钮存在重复入口（设置出现两次）。

## 4. 目标架构

### 4.1 分层

```text
物理输入
  ├─ keyboard
  ├─ pointer / mouse
  ├─ touch / pen
  ├─ menu / toolbar
  └─ programmatic (plugin, deep link, test)
        │
        ▼
Input Router
  ├─ 归一化平台/键位/IME/重复键
  ├─ 解析 scope + when + priority
  └─ 绑定 keymap
        │
        ▼
Action Dispatcher
  ├─ enabled / permission
  ├─ 执行 / 错误 / 日志
  └─ 返回 handled
        │
        ▼
Action Registry
  └─ 语义 ActionId + 元数据 + 默认 bindings
        │
        ├─ Desktop presentation: menu / toolbar / shortcut hint
        └─ Mobile presentation: tab / bottom sheet / FAB / gesture
```

### 4.2 Action 是唯一语义单位

```ts
type ActionId = string & { readonly __actionId: unique symbol };

type ActionScope = "global" | "editor" | "panel" | "dialog" | "mobile";
type InputPlatform = "desktop" | "mobile" | "web";
type InputDevice = "keyboard" | "pointer" | "touch" | "programmatic";

type ActionDefinition = {
  id: ActionId;
  title: string;
  category: string;
  scope: ActionScope;
  platforms: InputPlatform[];
  defaultBindings: Binding[];
  run: (ctx: ActionContext) => void | Promise<void>;
  enabled?: (ctx: ActionContext) => boolean;
  showInCommandPalette?: boolean;
  mobile?: {
    surface: "tab" | "bottom-sheet" | "fab" | "overflow";
    icon?: string;
  };
};
```

ActionId 使用 `domain.verb` 命名，例如：

```text
document.save
document.undo
search.open
settings.open
panel.outline.toggle
board.open
theme.open
workspace.create
workspace.open
```

### 4.3 Binding 与平台分离

```ts
type Binding =
  | {
      kind: "key";
      platform: "desktop" | "web";
      key: string;
      code?: string;
      ctrl?: boolean;
      meta?: boolean;
      alt?: boolean;
      shift?: boolean;
      scope: ActionScope;
      when?: string;
    }
  | {
      kind: "gesture";
      platform: "mobile";
      gesture: "long-press" | "swipe-left" | "swipe-right" | "double-tap";
      target?: string;
    }
  | {
      kind: "surface";
      platform: "desktop" | "mobile";
      surface: "menu" | "toolbar" | "tabbar" | "bottom-sheet" | "command-palette";
    };
```

关键点：

- 键盘绑定用 `code`（物理键）作为主键，`key` 作为显示/回退；
- `ctrl` 与 `meta` 分开，不再用 `mod` 混淆；
- binding 带 scope/when，不在命令实现里判断 UI 状态；
- mobile binding 只描述手势/界面入口，不冒充键盘；
- 用户覆盖以 `ActionId + platform + scope` 为键。

### 4.4 Keymap profile 与用户覆盖

按 ADR-007 的序列化边界：

- 默认绑定和用户 `keymap.toml` 使用 TOML，便于手写和注释；
- 运行时解析后的 `KeymapProfile` 以 JSON 对象在内存/IPC 中传递；
- 不维护第二份同权的 JSON 覆盖文件。

```text
keymap/
  default-desktop.toml
  default-mac.toml
  default-mobile.toml
keymap.toml              # 用户覆盖，由 Rust config service 读写
```

解析顺序：

```text
user override (keymap.toml)
  > platform default (default-*.toml)
  > fallback default
```

用户文件示例：

```toml
version = 2

[[bindings]]
action = "search.open"
platform = "desktop"
key = "p"
ctrl = true

[[bindings]]
action = "search.open"
platform = "mac"
key = "p"
meta = true

[[bindings]]
action = "search.open"
platform = "mobile"
surface = "header-button"
```

前端通过 Tauri command 读取解析后的 JSON 视图；写回用户文件时由 Rust `toml_edit` 只修改目标 binding，保留注释和格式。冲突检测在加载时完成：

- 同平台、同 scope、同 when 下多个 action 绑定相同输入 → 冲突；
- 用户覆盖导致冲突 → 在设置页提示，不静默丢弃；
- 插件 action 与核心 action 冲突 → 保留核心，插件标记 disabled 并记录 owner。

### 4.5 Input Router

```ts
type NormalizedInput = {
  source: "keyboard" | "pointer" | "touch" | "menu" | "programmatic";
  phase: "down" | "up" | "tap" | "long-press" | "command";
  code?: string;
  key?: string;
  ctrl?: boolean;
  meta?: boolean;
  alt?: boolean;
  shift?: boolean;
  composing: boolean;
  repeat: boolean;
  target?: string;
  scope: ActionScope;
};
```

规则：

1. `composing === true` 时，键盘输入优先交给 IME，不触发快捷键；
2. `repeat === true` 时，只有声明 `repeatable` 的 action 才重复执行；
3. 在 `input/textarea/contenteditable` 中，scope 为 `global` 的输入默认不触发，除非显式声明 `allowInEditable`；
4. 只有 Router 返回 `handled` 时才 `preventDefault`；
5. 所有输入最终转换为 `ActionInvocation`，Command/Intent 只是兼容适配器。

### 4.6 桌面与移动 presentation

同一个 Action 由不同平台呈现：

| Action | Desktop | Mobile |
|---|---|---|
| `settings.open` | 工具栏按钮 + `Ctrl/Cmd + ,` | 底部“设置”tab |
| `search.open` | 菜单 + `Ctrl/Cmd + P` | 顶部搜索按钮 |
| `panel.outline.toggle` | 视图菜单 + shortcut | 大纲 bottom sheet |
| `board.open` | 菜单 + shortcut | 顶部看板入口 |
| `document.save` | `Ctrl/Cmd + S` | 编辑页“保存”按钮 / 离开自动保存 |
| `theme.open` | 主题菜单 | 主题 bottom sheet |

移动端不渲染“桌面快捷键提示”，但保留 action 名称、图标和可用条件；桌面端从 keymap 生成 shortcut hint，而不是在组件里写死。

## 5. 移动端体验一致性规则

### 5.1 共享 action，分离 presentation

移动和桌面共享 ActionId、enabled、错误处理和日志；只分离：

- 入口位置；
- 输入方式；
- 布局容器；
- 是否显示快捷键提示。

### 5.2 导航与返回

移动端需要显式导航模型：

```text
workspace
  └─ map
      └─ document
          └─ editor
```

- 进入 document 压栈；
- 系统返回键/浏览器 back 弹出；
- 深链恢复 `tab + documentId`；
- 切换 tab 不丢失 document 状态；
- 退出编辑前走统一的 `requestClose`/save 流程。

### 5.3 状态持久化

移动端需要持久化：

```text
mobile.tab
mobile.documentId
mobile.editing
mobile.scrollTop (per document)
```

与桌面 `activePanelId` 分开保存，避免把 dock 概念硬塞进移动端；但两者都来自同一个 session 版本。

### 5.4 触控与安全区

- 最小触控目标 44×44；
- 使用 `env(safe-area-inset-*)`；
- 软键盘弹出时使用 `visualViewport`/`100dvh`，不让编辑器被遮挡；
- 长按/滑动要有明确反馈，不能与全局 `contextmenu` 屏蔽冲突；
- tabbar 不重复放置“设置”等已在头部出现的入口。

### 5.5 输入模式

编辑器和移动端应区分：

```text
browse mode
edit mode
selection mode
command mode
```

不同模式下同一输入的语义不同，例如方向键在编辑模式移动光标，在浏览模式切换文档；这种差异必须由 scope + mode 表达，而不是散落在组件 `onKeyDown` 中。

## 6. 分阶段实施建议

### Phase 0：建立事实与测试基线

- 盘点所有 `keydown`、`contextmenu`、`click` 入口；
- 为现有桌面快捷键写解析快照测试；
- 记录移动端所有入口与对应 action；
- 建立“无重复 action id / 无未注册 shortcut”的 fitness test。

### Phase 1：Action Registry + Keymap Core

- 定义 `ActionDefinition`、`Binding`、`KeymapProfile`；
- 将 `navCommands`、插件命令迁移为 action；
- 保留 `CommandDefinition` 兼容层；
- 实现 Input Router 与冲突检测；
- 统一 `preventDefault` / `composing` / `repeat` 规则。

### Phase 2：桌面接入

- 工具栏/菜单从 action 读取 label 和 shortcut hint；
- 全局 keydown 只保留 Input Router 一个入口；
- 删除 `matchesShortcut` 和命令上的 `shortcut` 字段；
- 命令面板由 action registry 生成。

### Phase 3：移动端接入

- MobileShell 使用 action registry；
- 增加移动导航栈与 session 恢复；
- 移除直接 `shellActions` 调用和重复按钮；
- 为移动端定义 default-mobile bindings（tab/bottom-sheet/gesture）。

### Phase 4：用户自定义与设置 UI

- 快捷键录制、冲突提示、重置；
- 按平台显示不同默认值；
- 导出/导入 keymap；
- 移动端“快捷操作”自定义（可选）；
- 插件 action 的输入能力声明。

### Phase 5：清理旧通道

- 删除未使用的 Intent 分支或合并到 Router；
- 删除全局 `contextmenu` 屏蔽，改为 scope 级菜单；
- 删除直接 `onKeyDown` 的重复实现，保留编辑器/对话框的局部输入语义；
- 更新 ADR 与测试矩阵。

## 7. 测试与 fitness functions

建议新增：

1. **Action registry 完整性**：所有可执行入口有 ActionId；没有重复 id。
2. **Binding 冲突检测**：同平台/scope/when 下无未解决冲突。
3. **平台矩阵**：desktop/mac/mobile 默认 keymap 快照。
4. **IME 保护**：composing 时快捷键不触发。
5. **编辑态保护**：input/contenteditable 中 global shortcut 不误触。
6. **移动导航**：进入/返回/恢复 tab 与 document。
7. **移动触控目标**：关键按钮 ≥ 44px。
8. **插件输入权限**：插件不能覆盖核心 action，冲突有 owner 记录。
9. **E2E**：桌面快捷键、移动 tab/返回、长按菜单。

## 9. 建议的决策

建议先确认以下产品决策，再进入实现：

1. 移动端首版是否只支持触控，还是也支持外接键盘/快捷键？
2. 用户自定义快捷键是否从桌面和移动端同时开放，还是先桌面？
3. 移动端“设置”入口保留在 header 还是 tabbar，是否允许同时存在？
4. 插件是否允许声明移动端 bottom-sheet/tab 入口，还是只允许 action 由 shell 自动放置？
5. 是否支持长按上下文菜单；如果支持，全局 `contextmenu` 屏蔽必须移除。

在这些决策确定前，不建议直接增加更多硬编码快捷键；先把 Action + Input Router 建起来，后续每个平台只增加 binding。

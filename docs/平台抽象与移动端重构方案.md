# 平台抽象与移动端重构方案

> 日期：2026-11-01  
> 状态：Phase 1 已实施；Phase 2 端口层完成；Phase 3 大部分实施；Phase 4 部分实施  
> 范围：前端运行时装配、Shell 组合、平台端口、Action/输入解耦、Rust 平台边界、移动端落地顺序  
> 基线：前端 217 / Rust 48 / E2E 37

## 1. 结论

当前移动端不是原生 App，而是桌面应用在窄窗口下切换出来的响应式 Shell。真正的问题不是“缺少一个 `if (mobile)`”，而是**平台假设散落在入口、Shell、文件选择、动作实现和 Rust 命令里**。

目标不是让桌面和移动看起来一样，而是：

> **语义耦合，实现解耦。**  
> 两端共享行为契约，不共享布局、触发器和平台实现。

具体约束：

- 平台身份只在**组合根**出现一次；
- 页面和业务不知道“移动端/桌面端”；
- 布局差异放在 Shell；
- 操作差异放在输入绑定和 Action；
- 文件、对话框、导航、分享、生命周期通过端口抽象；
- 平台专属能力通过 Action 注册表达，而不是 UI 里分支；
- Rust 业务 crate 保持平台无关，只有入口和 adapter 知道平台。

## 2. 差异分层

| 差异类型 | 例子 | 归属 | 是否共享 |
|---|---|---|---|
| 布局不同 | 桌面 Dockview + 多面板；移动单列 + 底栏 | Shell / Frame | 否 |
| 触发方式不同 | 桌面右键 / F2；移动长按 / 左滑 | Binding / Input Adapter | 否 |
| 行为相同 | 都调用“重命名文档” | Application Use Case | 是 |
| 呈现不同 | 桌面模态框；移动底部输入面板 | Dialog / Presenter Port | 行为共享，呈现不同 |
| 业务规则不同 | 桌面永久删除；移动只允许回收站 | Policy 或独立 Action | 显式建模，不藏 `if` |

判断标准：

1. 页面组件里不出现 `isMobile` / `platform.kind`；
2. use case 里不出现路径、Tauri、DOM；
3. 两端不复制重命名、删除、保存逻辑；
4. 新增一种触发方式不需要改业务代码。

```text

                │ 使用共享页面
┌───────────────▼────────────────────────────────────┐
│ Pages                                               │
│ LibraryPage / DocumentPage / MapPage / SettingsPage │
└───────────────┬────────────────────────────────────┘
                │ 只依赖端口
┌───────────────▼────────────────────────────────────┐
│ Application                                         │
│ Use Cases / Stores / Ports / Action Registry        │
└───────────────┬────────────────────────────────────┘
                │
┌───────────────▼────────────────────────────────────┐
│ Domain / Kernel                                     │
│ 文档模型 / Command / 插件契约 / Panel 协议            │
└───────────────┬────────────────────────────────────┘
                │
```

依赖方向：

```text
ui/pages ──► application/ports
ui/shell ──► runtime
runtime  ──► infrastructure adapters
domain   ◄── application
```

`domain` 不依赖平台；`application` 不依赖具体 adapter；只有 runtime 同时接触 UI 和基础设施。

## 4. Runtime 契约

建议新增：

```text
src/runtime/
  contracts.ts
  useRuntime.ts
  createRuntime.ts
  createDesktopRuntime.ts
  createMobileRuntime.ts
  index.ts
```

> Phase 1 当前实现：`useRuntime` + `createRuntime` + `DesktopShell` / `MobileRuntimeShell` + `ShellProps`。
> Phase 2 已实现：`RuntimeServices`、`RuntimeProvider`、Library/Dialog/DocumentActions 端口；
> `WorkspacePresenter` 与 `createBrowserRuntime` 尚未实现。

核心类型：

```ts
export type RuntimeServices = {
  library: LibraryPort;
  dialogs: DialogPort;
  navigation: NavigationPort;
  presenter: WorkspacePresenter;
  lifecycle: LifecyclePort;
  sharing?: SharePort;
};

export type Runtime = {
  Shell: ComponentType;
  services: RuntimeServices;
  capabilities: PlatformCapabilities;
};
```

入口只做一次装配：

```tsx
const runtime = await createRuntime();

<RuntimeProvider value={runtime}>
  <runtime.Shell />
</RuntimeProvider>
```

`createRuntime()` 内部可以做平台判断，但这是**唯一允许**的位置。进一步可以改成构建时入口别名，把运行时判断也消掉：

```text
main.desktop.tsx → createDesktopRuntime
main.mobile.tsx  → createMobileRuntime
```

第一阶段先保留运行时组合根，避免同时改构建链。

## 5. Shell 契约

Shell 只负责结构，不负责业务：

```tsx
// DesktopShell
<DesktopFrame
  header={<DesktopHeader />}
  side={<WorkspaceSidebar />}
  content={<ActivePage />}
/>

// MobileShell
<MobileFrame
  header={<CompactHeader />}
  bottom={<BottomTabs />}
  content={<ActivePage />}
/>
```

共享页面：

```text
LibraryPage
DocumentPage
MapPage
SettingsPage
```

要求：

- `DocumentPage` 同时服务桌面和移动；
- 桌面和移动的差异通过 slots / Frame 表达；
- 不复制编辑器；
- 移动端 lazy load 编辑器可以，但不 fork 编辑器。

`App.tsx` 最终不再出现：

```tsx
{shell.kind === "mobile" ? <MobileShell /> : <DockWorkspace />}
```

也不再无条件渲染 `AppToolbar`。

## 6. 端口设计

### 6.1 LibraryPort

```ts
export type LibraryId = string;

export type LibrarySummary = {
  id: LibraryId;
  title: string;
  source: "external" | "managed";
};

export interface LibraryPort {
  list(): Promise<LibrarySummary[]>;
  open(id: LibraryId): Promise<WorkspaceView>;
  create(): Promise<LibrarySummary | null>;
  importLibrary(): Promise<LibrarySummary | null>;
  exportLibrary(id: LibraryId): Promise<void>;
}
```

桌面 adapter：

- 系统文件对话框；
- 外部 `.note` 路径；
- 直接打开外部文件。

移动 adapter：

- 系统导入面板；
- 复制到 App 私有书库；
- 用 managed id 打开；
- 导出走分享面板。

页面不接触路径。

### 6.2 DialogPort

```ts
export interface DialogPort {
  confirm(options: ConfirmOptions): Promise<boolean>;
  prompt(options: PromptOptions): Promise<string | null>;
}
```

- 桌面：模态对话框；
- 移动：底部 sheet / 全屏输入；
- 动作代码只调用端口。

### 6.3 NavigationPort

```ts
export interface NavigationPort {
  back(): boolean;
  openDocument(id: DocumentId): void;
  canGoBack(): boolean;
}
```

- 桌面按钮和移动右滑调用同一个 `back()`；
- 不出现“移动端才维护返回栈”的业务分支。

### 6.4 WorkspacePresenter

这是当前代码里最容易被忽略的耦合点。

```ts
export interface WorkspacePresenter {
  present(view: WorkspaceView): void;
  resetLayout(): void;
}
```

- 桌面实现：打开 Dockview 面板；
- 移动实现：写入移动导航状态；
- `useWorkspaceOpen` 不再直接操作 `dockRef`。

### 6.5 LifecyclePort

```ts
export interface LifecyclePort {
  onBackground(handler: () => void): () => void;
  onForeground(handler: () => void): () => void;
  onBeforeClose(handler: () => void): () => void;
}
```

用于：

- 移动端切后台自动保存；
- 桌面关窗保存；
- 恢复前台刷新。

### 6.6 PlatformCapabilities

```ts
export type PlatformCapabilities = {
  fileModel: "external-path" | "managed-library";
  share: boolean;
  fileAssociation: boolean;
  safeArea: boolean;
  virtualKeyboard: boolean;
  multipleWindows: boolean;
};
```

注意：capabilities 只用于**装配和 Action 可用性**，不应在页面里到处分支。这里刻意不提供 `kind: "desktop" | "mobile"`；能布局的 Shell 已经由 runtime 注入，业务不需要再知道平台名字。

## 7. Action 与输入解耦

现有 `src/kernel/action` 已经是正确基础，继续沿用它：

- Action 只注册一次；
- Binding 按平台/输入方式注册；
- 手势和菜单只产生 Action，不直接调用 service。

示例：

```ts
registerAction({
  id: "document.rename",
  run: async (context) => {
    const title = await context.dialogs.prompt({ ... });
    if (!title) return;
    await context.documents.rename(context.documentId, title);
  },
});
```

绑定：

```text
desktop: F2 / 右键菜单
mobile:  长按 / 左滑动作面板
```

两端都调用：

```ts
runAction("document.rename")
```

平台能力通过注册表达：

```ts
if (runtime.sharing) {
  registerAction({ id: "library.share", ... });
}
```

没有分享能力的平台不出现该 Action，页面不需要 `if (mobile)`。

## 8. Rust 侧边界

### 8.1 业务 crate 保持平台无关

继续共享：

```text
crates/storage
crates/document
crates/workspace
crates/content
crates/board
crates/import
crates/theme
crates/plugin-*
```

### 8.2 入口拆分

```text
src-tauri/src/
  lib.rs          # 公共 run()
  desktop.rs      # 窗口、single-instance、文件关联
  mobile.rs       # 移动 setup、分享、导入
  commands/       # 公共命令
```

```rust
pub fn run() {
    #[cfg(desktop)]
    desktop::run();

    #[cfg(mobile)]
    mobile::run();
}
```

桌面专属插件只出现在 `desktop.rs`。

### 8.3 AppState 注入 trait

```rust
pub struct AppState {
    pub library: Arc<dyn LibraryStore>,
    pub paths: Arc<dyn Paths>,
    pub share: Option<Arc<dyn Share>>,
}
```

命令只依赖 `AppState`，不写 `#[cfg(mobile)]`。

### 8.4 LibraryStore

```rust
pub trait LibraryStore: Send + Sync {
    fn open(&self, id: &LibraryId) -> Result<Workspace, String>;
    fn import(&self, source: &Path) -> Result<LibraryId, String>;
    fn export(&self, id: &LibraryId) -> Result<PathBuf, String>;
}
```

桌面实现使用外部路径；移动实现使用 App 私有目录。

### 8.5 兼容策略

当前 `WorkspaceView.root` 和大量命令仍以路径字符串为主。不要一次改完：

1. 先让前端只通过 `LibraryPort` 访问；
2. 再在 Rust 边界引入 `LibraryId`；
3. 内部仍可保留 `PathBuf`；
4. UI 永远不显示内部路径。

## 12. 场景验证

### 场景 A：布局不同，行为相同

- 桌面：Dockview + 侧栏；
- 移动：单列 + 底栏；
- 共享：`DocumentPage`、保存、重命名、删除；
- 结论：解耦。

### 场景 B：操作不同，行为相同

- 桌面：F2 / 右键；
- 移动：长按 / 左滑；
- 共享：`document.rename` Action；
- 结论：解耦。

### 场景 C：行为不同

- 桌面：永久删除；
- 移动：仅移到回收站；
- 处理：拆 Action 或注入 `DeletePolicy`；
- 结论：仍解耦，但必须显式建模，不能藏在 UI `if`。

### 场景 D：文件模型不同

- 桌面：外部 `.note`；
- 移动：App 私有书库；
- 处理：`LibraryPort`；
- 结论：解耦。

## 14. 非目标

- 不复制一套移动端 store/service；
- 不为移动端 fork 编辑器；
- 不把 `PlatformAdapter` 做成万能接口；
- 不强行让两端 UI 一样；
- 不在业务 use case 里判断平台；
- 不在初始化 Android 之前大改 Rust 入口。

## 19. 待讨论：远程笔记与多端同步

状态：**待讨论，不进入当前 Phase 0–6。**

场景：

- 手机和电脑编辑同一个笔记；
- 需要离线写作；
- 需要处理两端同时修改同一段/同一块；
- 可能涉及附件、共享、端到端加密。

当前只记录约束，不选型：

- 不同步正在打开的 SQLite/WAL 文件；
- 不把 `.note` 文件级同步当作主协议；
- 先确认是“交替编辑”还是“同段实时合并”；
- 再决定块级同步、CRDT、服务端或托管方案。

进入讨论前需要确认：

1. 是否需要同一段落实时合并；
2. 个人多设备还是多人共享；
3. 自建服务端还是托管；
4. 是否要求端到端加密；
5. 图片/附件是否同步。

## 1. 交付目标与范围

### 1.1 目标

在保持 `.note` 单文件知识库和现有功能语义不变的前提下，将应用收敛为：

```text
稳定内核 + 功能插件 + 能力插件 + 数据插件
```

### 1.2 范围

- 功能插件：board、reference、import、viewport、theme、help、search。
- 能力插件：dialog、fs、clipboard、single instance、image asset protocol、file association。
- 数据插件：`.tnlook` 外观包、模板、图标集。
- 平台：Windows、macOS、Linux。移动端不作为本期目标。

### 1.3 非目标

- 不引入运行时动态加载任意代码。
- 不重写编辑器、文档、导图的业务语义。
- 不开放未经审计的第三方原生插件。
- 不改变 `.note` 存储格式。

### 1.4 当前基线

本手册描述的实施阶段已完成。当前维护基线：

## 2. ADR 决策记录

以下决策在实施期间固定，除非出现新的不可逆证据，否则不再重新讨论。

### ADR-001 编译期模块化单体

- **决策**：功能插件与能力插件在编译期集成，不做运行时动态加载。
- **理由**：保持单文件便携安装，避免任意代码执行和外部残留。
- **影响**：插件以 crate / workspace package 形式存在，通过 manifest 声明贡献点。

### ADR-002 插件分三类

- **决策**：功能插件、能力插件、数据插件三种模型，生命周期和权限不同。
- **理由**：代码插件和数据插件不能共用同一安全边界。

### ADR-003 主题与皮肤统一为 `.tnlook`

- **决策**：一个外观包同时承载主题 token 与皮肤资源。
- **理由**：用户只面对一个“外观”，避免主题/皮肤不匹配和双文件管理。

### ADR-004 数据插件不执行代码

- **决策**：`.tnlook`、模板、图标集只解析数据，禁止脚本、任意 CSS 选择器和远程资源。
- **理由**：数据包是可分享边界，必须可校验、可回退。

### ADR-005 外观作用域

- **决策**：本期支持全局 + 当前知识库；导图级预留。
- **理由**：先满足知识库级换肤，避免过度复杂。

### ADR-006 平台目标

- **决策**：Windows / macOS / Linux 为目标平台，移动端非目标。
- **理由**：聚焦桌面便携安装，Tauri 移动端差异另立项目评估。

### ADR-007 插件间禁止直接 import

- **决策**：插件只通过命令、事件、端口通信。
- **理由**：消除插件间的隐藏耦合。

### ADR-008 `.note` 是唯一内容真相

- **决策**：插件化不改变 SQLite 存储格式，插件数据放在扩展表和独立命名空间。
- **理由**：保护用户数据和现有文件兼容。

### ADR-009 第三方 JS 插件暂不开放

- **决策**：本期不加载第三方 JS；未来若开放，必须运行在沙箱 Worker 并声明能力。
- **理由**：安全边界优先于扩展性。

### ADR-010 核心领域能力属于内核

- **决策**：workspace、document、map、storage、session、appearance 是核心领域能力，属于内核；board、reference、import、viewport、theme、help、search 是可插拔功能。
- **理由**：消除“内核不包含业务”与“文档/导图属于内核”之间的措辞矛盾。
- **影响**：内核承载不可移除的领域语义；功能插件承载可插拔的产品能力。

### ADR-011 深耦合扩展点是一等契约

- **决策**：BlockTypeExtension 与 MapNodeType 作为内核扩展点，在 Phase 2 先行定稿，不按普通 UI 贡献点处理。
- **理由**：编辑器 block 和导图节点与内核强耦合，错误抽象会造成隐性依赖。

### ADR-012 版本与兼容

- **决策**：插件 API 采用语义化版本；`.note`、外观包、插件存储 schema 均带版本；破坏性变更必须提供迁移。
- **理由**：可验证的兼容边界是长期插件化的前提。

### ADR-013 Monorepo 构建边界

- **决策**：采用 pnpm workspaces + cargo workspace；最终仍输出单个可执行文件。
- **理由**：拆分模块的同时保持单文件便携安装。

## 4. 插件契约规范

### 4.1 插件清单 Schema

```json
{
  "schema": 1,
  "id": "board",
  "name": "对照板",
  "version": "1.0.0",
  "kind": "feature",
  "provides": ["board"],
  "dependencies": [],
  "capabilities": ["board.read", "board.write"],
  "contributes": {
    "commands": ["board.open", "board.pin"],
    "panels": ["board.panel"],
    "toolbarItems": ["board.menu"],
    "contextMenuItems": [],
    "settingsSections": [],
    "blockTypes": [],
    "mapNodeTypes": [],
    "appearancePacks": [],
    "migrations": ["board.migration.v1"]
  }
}
```

校验规则：

- `id` 只能是小写字母、数字、连字符；
- `kind` 只能是 `feature | capability | data`；
- `capabilities` 必须落在内核能力白名单内；
- `dependencies` 必须能被解析；
- 循环依赖直接拒绝；
- 重复 `id` 直接拒绝；
- 未知字段拒绝；
- `provides` 与 `dependencies` 一致。

### 4.2 生命周期

```text
register
  → resolveDependencies
  → validateCapabilities
  → activate(context)
  → running
  → deactivate(context)
  → unregister
```

约束：

- `activate` 必须幂等；
- `deactivate` 必须释放所有资源；
- 激活失败不得留下半初始化状态；
- 停用后 UI 贡献点必须立即消失。

### 4.3 前端 SDK

```ts
registerCommand(def)
registerPanel(def)
registerToolbarItem(def)
registerContextMenu(def)
registerSettingsSection(def)
registerBlockType(def)
registerMapNodeType(def)
registerAppearancePack(def)
registerMigration(def)
```

所有 `def` 必须包含：

```text
id
version
ownerPlugin
```

### 4.4 后端 API

```rust
trait AppPlugin {
    fn id(&self) -> &'static str;
    fn register(&self, builder: Builder) -> Builder;
    fn migrate(&self, ctx: &MigrateContext) -> Result<(), PluginError>;
}
```

### 4.6 错误与命名

- 命令：`domain.action`；
- 事件：`domain.object.pastTense`；
- 端口：`DomainRepository`；
- 插件 id：kebab-case；
- 错误码：`PLUGIN_<ID>_<CODE>`。

错误分类：

| 类别 | 示例 | 处理 |
| --- | --- | --- |
| 契约错误 | 未知命令、坏事件 | 记录并忽略 |
| 校验错误 | 外观包不合法 | 拒绝导入 |
| 能力错误 | 权限不足 | 拒绝执行 |
| 存储错误 | 迁移失败 | 回滚 |
| 平台错误 | 文件关联失败 | 用户可恢复 |

### 4.7 组合根与依赖注入

- `App.tsx` 和 `lib.rs` 只做组合根，不写业务；
- 插件通过 `activate(context)` 获取内核服务；
- 内核服务通过 trait 暴露，不暴露具体结构；
- 前端 store 只由拥有者插件读写；
- 插件状态独立命名，不共享可变对象。

组合根职责：

```text
读取启用插件列表
实例化内核
按依赖顺序激活插件
挂载 UI 外壳
处理激活失败
```

### 4.8 安全模型

- 能力插件：编译期授权；
- 功能插件：编译期打包，只访问 SDK；
- 数据插件：只解析、校验、渲染；
- 资源：本地路径、SVG 清洗、ZIP 限制、MIME 校验；
- 未来第三方 JS：沙箱 Worker + 能力声明；
- 文件关联：仅用户显式勾选。

### 4.9 可观测性

- 命令执行日志；
- 插件生命周期日志；
- 事件发布统计；
- 错误码与堆栈；
- 外观资源加载耗时；
- 控制台面板统一消费上述日志。

## 5. 外观包规范

### 5.1 文件结构

```text
starry-glass.tnlook
├─ appearance.json
├─ preview-dark.webp
├─ preview-light.webp
└─ assets/
   ├─ wallpaper-dark.webp
   ├─ wallpaper-light.webp
   ├─ decoration-left.webp
   ├─ texture.png
   └─ brand.svg
```

### 5.2 `appearance.json`

```json
{
  "schema": 1,
  "id": "starry-glass",
  "name": "星空玻璃",
  "version": "1.0.0",
  "author": "local",
  "modes": ["dark", "light"],
  "variants": {
    "dark": {
      "theme": {
        "colors": {},
        "typography": {},
        "shape": {}
      },
      "skin": {
        "background": {},
        "decorations": [],
        "surfaces": {},
        "components": {},
        "map": {}
      }
    },
    "light": {}
  }
}
```

### 5.3 资源规则

- 只允许本地资源；
- 允许 WebP / AVIF / PNG / SVG；
- SVG 必须清洗；
- 单资源不超过预算；
- ZIP 解压后总量不超过预算；
- 资源路径必须相对且可校验；
- 缺失资源回退到默认外观。

### 5.4 Token 目录

外观包最终解析为稳定 token：

```text
surface.canvas
surface.panel
surface.panel.alpha
surface.dialog
surface.editor
surface.hover
text.primary
text.muted
accent
accent.contrast
border.subtle
shadow.panel
shadow.dialog
blur.panel
map.canvas
map.edge
map.node.surface
tab.active.background
```

组件只消费 token，不感知具体外观。

### 5.5 校验

导入时必须：

- 校验 schema；
- 校验资源存在；
- 校验对比度；
- 校验性能预算；
- 生成预览；
- 失败则拒绝导入，不得部分应用。

### 5.6 制作方式

- 普通用户：可视化外观编辑器，生成 `.tnlook`；
- 进阶用户：编辑 `appearance.json` + `assets/`，由应用校验打包；
- 微调：设置中保存 override，不生成新外观包。

### 5.7 应用与回退

- 应用是原子操作：先解析成功，再整体切换；
- 切换失败回退到上一个外观；
- 缺失资源回退到默认经典外观；
- 切换不重建编辑器、导图和面板。

## 6. 平台适配器规范

内核通过 `PlatformAdapter` 隔离平台差异：

```rust
trait PlatformAdapter {
    fn home_dir(&self) -> Result<PathBuf, PlatformError>;
    fn cache_dir(&self) -> Result<PathBuf, PlatformError>;
    fn data_dir(&self) -> Result<PathBuf, PlatformError>;
    fn open_path(&self, path: &Path);
    fn reveal_path(&self, path: &Path);
    fn register_file_association(&self, exe: &Path);
    fn unregister_file_association(&self);
    fn system_theme(&self) -> SystemTheme;
}
```

平台实现：

| 平台 | 文件关联 | WebView | 数据目录 |
| --- | --- | --- | --- |
| Windows | 注册表 | WebView2 | exe 同级 `data/` |
| macOS | LaunchServices | WKWebView | `Application Support` |
| Linux | desktop entry | WebKitGTK | XDG 目录 |

约束：

- 内核不写 `#[cfg(windows)]` 业务分支；
- 平台分支只存在于适配器实现；
- 能力插件通过条件编译提供平台实现。

## 7. 分阶段实施计划

### Phase 0：工程脚手架

- 建立 pnpm workspaces 和 cargo workspace；
- 建立内核、SDK、插件目录骨架；
- 保持现有应用可构建、可运行。
- **退出条件**：现有 133/38/33 基线通过。
- **实施细分**：0A 契约、0B 命令内核、0C cargo workspace、0D 事件内核、0E 面板内核、0F 插件装配器、0G Theme 激活、0H Provider 组合根、0I 工具栏宿主、0J Theme UI 迁移、0K 设置区宿主、0L Board 插件、0M 平台适配器/workspace 骨架、0N Dockview 延迟挂载；实际记录见《插件化实施记录》。
- **实施备注**：若 pnpm 工具链不可用，可保留 npm 单包，先完成 Cargo workspace；pnpm 切换作为独立任务，不阻塞内核契约。

### Phase 1：内核 + 平台适配器

- 抽取 `PlatformAdapter`；
- 收敛窗口、路径、文件关联、拖放；
- 保留单文件便携安装。
- **退出条件**：Windows 行为不变，三平台编译配置齐全。
- **进展**：主题路径与文件关联已接入 PlatformAdapter；.tnlook ZIP 读取、manifest 校验、导入入口、颜色应用/回退、启动恢复、壁纸背景层、装饰层（含 hideBelow）、玻璃表面、Dockview 表面、IndexedDB 持久化与优先级/回退 UX 已建立。

### Phase 2：插件契约与贡献点

- 实现 manifest 解析、生命周期、注册表；
- 实现命令、事件、端口目录；
- 实现空插件加载/卸载。
- **退出条件**：契约单测通过，空插件可激活停用。
- **进展**：theme、board、reference、search、help、import、viewport 已插件化并装配；reference 已提供设置区贡献；设置弹窗已由 SettingsHost 统一挂载，兼容 shim 已清零。

### Phase 3：theme 参考插件

- 外观引擎入内核；
- theme 作为功能插件贡献设置、导入导出；
- `.tnlook` 数据管线建立。
- **退出条件**：现有主题功能无回归，导入导出可用。

### Phase 4：迁移功能插件

按顺序迁移：

```text
board → reference → import → viewport → help → search
```

每个插件迁移后执行完整回归。

- **退出条件**：所有功能以插件形式注册，无直接 import。

### Phase 5：外观包流水线

- 导入、校验、预览、应用、回退；
- 对比度、资源、性能校验；
- **退出条件**：恶意包被拒绝，缺失资源回退。

### Phase 6：收尾

- 迁移、回滚、文档、CI；
- 三平台构建与安装验证。
- **退出条件**：交付检查清单全部通过。

## 8. 迁移与回滚

### 8.1 数据兼容

- `.note` 文件格式不变；
- 旧 `ThemeManifest schema 1` 迁移为最小外观包；
- 旧 localStorage 主题迁移到文件；
- 插件扩展表带 schema 版本。

### 8.2 迁移顺序

```text
核心迁移 → 插件迁移
依赖插件先于被依赖插件迁移
```

### 8.3 回滚

- 插件激活失败：回滚到激活前状态；
- 迁移失败：保留迁移前数据，记录版本；
- 外观应用失败：回退到上一个外观；
- 回滚必须可验证。

### 8.4 功能开关

- 插件可禁用；
- 禁用后贡献点消失；
- 禁用后数据保留；
- 禁用期间不执行该插件迁移。

## 12. 交付说明

实施者应严格按 Phase 顺序推进，每阶段只交付一个可验证结果，并在每阶段末跑完整回归。

若发现契约设计无法落地，应更新 ADR 和本手册，而不是绕过契约直接改内核。

本手册是执行依据；《技术架构与插件化方案》是目标蓝图；两者冲突时以本手册为准，但需同步修订蓝图。
